# Hunter SaaS 原型公共设计语言与组件体系

## 1. 工程原则

本原型不是由 60 个页面分别堆叠 HTML。页面采用“薄页面壳 + 演示数据 + 公共组件 + 设计 Token”的结构：

1. 页面只负责业务编排、路由参数和操作结果。
2. 视觉规则由全局 Token 和分层样式统一维护。
3. 可复用交互只在公共组件中实现，业务页不得重新实现按钮、输入、选择、表格、浮层和反馈。
4. 所有图标均由本地 `Icon` 组件输出 SVG，不依赖 Icon Font、Emoji、外部 CDN 或第三方图标包。
5. 演示对象和跨页状态由统一数据文件及 Store 管理，避免同一候选人、岗位或任务在不同页面出现冲突。

## 2. 设计 Token

| 层级       | 文件                        | 内容                                                                     |
| ---------- | --------------------------- | ------------------------------------------------------------------------ |
| 基础 Token | `src/styles/tokens.css`     | 浅色、深色的背景、文字、边界、品牌色、语义色、阴影、圆角、间距和动效时长 |
| 页面基础   | `src/styles/base.css`       | 字体、排版、焦点、滚动条和全局基础行为                                   |
| 产品框架   | `src/styles/layout.css`     | 用户端、运营端导航、顶栏、内容容器和移动端框架                           |
| 公共组件   | `src/styles/components.css` | 按钮、输入、选择、表格、浮层、分页、Toast 和状态组件                     |
| 业务组件   | `src/styles/business.css`   | 业务主线、任务过程、证据、匹配卡和统计区域                               |
| 页面编排   | `src/styles/pages.css`      | 仅包含页面布局，不重新定义公共控件                                       |
| 响应式     | `src/styles/responsive.css` | 桌面、iPad、iPhone 的结构变化和信息重排                                  |

设计方向为已审批的 **WorkBuddy × Vercel AI 任务空间**：冷色中性底、蓝色行动色、紧凑而克制的信息密度、清晰的任务状态和低干扰动效。警告、错误等语义状态允许使用暖色，但不用于装饰。

### 2.1 字号与可读性门禁

1. 所有用户可见文字不得小于 `12 CSS px`，包括辅助说明、时间、状态标签、表格元数据、Tooltip 和 Modal 内容。
2. 中文正文默认使用 `14px`；辅助正文使用 `12–13px`；按钮、输入框和选择项不低于 `12px`。
3. 不通过缩放页面、压缩字距或使用低于门槛的字号维持信息密度。空间不足时优先调整布局、截断、换行或按需展开。
4. 每次视觉回归同时检查普通密度显示器和高分屏；只在高分屏上勉强可见不视为通过。

## 3. 产品级公共组件

| 层级     | 组件                                             | 统一能力                                                         |
| -------- | ------------------------------------------------ | ---------------------------------------------------------------- |
| 基础命令 | `Button`、`IconButton`                           | 尺寸、图标、主次层级、危险态、Loading、Disabled、Hover、Focus    |
| 输入     | `Input`、`Textarea`、`SearchInput`               | 标签、帮助信息、错误态、搜索提交和键盘行为                       |
| 选择     | `Select`、`MultiSelect`、`Cascader`、`DateRange` | 单选、多选、多级选择、日期范围、点击外部关闭和清空               |
| 布尔选择 | `Checkbox`、`Radio`、`Switch`                    | 自定义 SVG 状态、键盘访问和禁用态                                |
| 导航     | `Tabs`、`Segmented`、`Pagination`                | 当前项、分页、禁用和响应式滚动                                   |
| 数据展示 | `DataTable`、`Status`、`Progress`、`Tooltip`     | 表头、截断、操作列、标签、进度和悬停说明                         |
| 浮层反馈 | `Modal`、`Drawer`、`Toast`                       | 焦点入口、遮罩、确认、关闭、错误和短视口滚动                     |
| 页面状态 | `EmptyState`、`PageHeader`、`FilterBar`          | Loading、Empty、Error、Disabled、Permission-limited 及页面命令区 |

组件实现在 `src/components/ui.jsx`，全部业务页面只能调用这些组件。

### 3.1 Modal 规范

Modal 根据任务复杂度使用四档标准尺寸，业务页面不得自行写宽度：

| 尺寸 | 最大宽度 | 使用范围                                         |
| ---- | -------- | ------------------------------------------------ |
| `sm` | 520 px   | 删除确认、单一风险确认和短提示                   |
| `md` | 680 px   | 单组输入、补充说明、授权和常规操作，作为默认尺寸 |
| `lg` | 900 px   | 多组配置、沟通记录、技术详情和需要对照的信息     |
| `xl` | 1080 px  | 公司、岗位、候选人、论文和专利的新建与编辑表单   |

统一行为：

1. 标题区、可滚动正文区和操作区相互独立；短视口只滚动正文，标题和操作按钮保持可见。
2. 桌面端正文内边距为 24 px，标题和操作区使用 22 px 横向内边距；移动端统一收敛为 14–16 px。
3. 移动端 Modal 使用底部面板布局并占满可用宽度，操作按钮等宽排列。
4. 新建和编辑同一业务对象必须复用同一份字段定义，只允许默认值、标题、提交文案和系统只读字段存在差异。
5. 所有可见输入、选择、日期和按钮都调用公共组件，不使用浏览器原生默认样式。

### 3.2 业务资产边界与表单

1. 独立业务资产包括公司、岗位、候选人、人才摸排、论文和专利。
2. 联系人从属于公司，在公司详情中新增和管理，不提供独立业务资产入口。
3. 招聘机会在信号和业务主线中审核、补充和转化，不作为独立业务资产。
4. `AssetForm` 统一承载业务资产及公司联系人的新建和编辑字段，避免两个入口随版本演进产生字段漂移。
5. 公司联系人由猎头自行沟通；Hunter 只保存资料和人工添加的沟通记录，不提供“开始沟通”动作。

## 4. 共享业务组件

| 组件                 | 使用范围                                                 |
| -------------------- | -------------------------------------------------------- |
| `InfoGrid`           | 公司、岗位、候选人、人才摸排、论文、专利及公司联系人详情 |
| `EvidenceList`       | 研究证据、关系证据、来源和可信度                         |
| `ActivityTimeline`   | 主线、任务、沟通和推进记录                               |
| `SummaryList`        | 任务、信号、导入和诊断摘要                               |
| `WorkstreamBoard`    | 客户开发、岗位招聘、人才摸排和候选人求职                 |
| `TaskProcess`        | Agent 与代码步骤、等待、失败、恢复和人工检查             |
| `CandidateMatchCard` | 人岗匹配判断、证据、风险和操作                           |
| `StatStrip`          | 工作台、详情和运营端的紧凑统计区域                       |

### 4.1 业务主线会话组件

| 组件                       | 统一能力                                                                       |
| -------------------------- | ------------------------------------------------------------------------------ |
| `ConversationWorkspace`    | 可收起业务主线导航、从首条用户输入逐条推进的对话、通用检查区和复杂结果全宽审核 |
| `MarkdownEvent`            | 普通进展、等待、结果、影响分析和授权的统一 Markdown 呈现                       |
| `InlineDataTable`          | 在对话中直接展示少量证据、联系人、字段差异和人物关系                           |
| `CommandReview`            | 展示自然语言解析后的原始指令、对象范围、批量规则、例外项和执行边界             |
| `WorkstreamRuntimePanel`   | 默认收起的执行计划与相关任务检查区                                             |
| `CandidateReviewWorkspace` | 跨渠道候选人完整审核、四类逐人决定、分数/建议批量操作和处理后只读复核          |
| `BusinessReviewWorkspace`  | 公司与联系人、招聘机会、人物关系、字段更新、影响范围和支线建议的通用完整审核区 |

业务主线只组合标准消息、标准产物和标准决策，不为客户开发、岗位招聘、人才摸排或候选人求职临时新增同义组件。`BusinessReviewWorkspace` 由 Schema 数据驱动，同一界面按业务对象展示字段、证据、可信度、缺失项、建议和审核决定。任务详情使用同一 `TaskProcess`，但客户机会核验、人才寻找、人才摸排和资料更新必须提供各自的过程数据，不能复用同一套日志。

### 4.2 业务判断与操作授权

1. 对话时间线只为账号、文件、平台读取、发送消息、申请好友和拨打电话等操作授权显示直接允许或拒绝按钮。
2. 公司、联系人、岗位、候选人、人物关系和资料字段等业务判断不得在时间线中直接确认。
3. 业务判断由自然语言回复，或由“打开审核”进入 `CandidateReviewWorkspace` / `BusinessReviewWorkspace` 处理。
4. 自然语言与审核界面必须进入同一业务命令，不能形成两套保存、授权和失败恢复逻辑。

## 5. 框架与状态

- `AppShell`：用户端导航、全局搜索、通知、新建菜单、主题切换和移动端底栏。
- `OpsShell`：运营端脱敏导航、权限提示和移动端横向导航。
- `PrototypeStore`：保存主题、主线、任务、通知、平台登录、自动化权限、导入和操作反馈；使用浏览器本地存储模拟跨页联动。
- `pageRegistry`：维护 45 个用户端页面和 15 个运营端页面的唯一编号、标题与路由。

## 6. 原型到正式代码的映射

研发实现时应保留以下映射：

1. 原型基础组件映射为正式 Design System 组件，不在业务页复制 JSX 和 CSS。
2. 业务组件映射为领域共享组件，业务 API 只替换演示数据和 Store，不改变已审批的信息结构。
3. 页面文件保持编排职责；发现组件缺口时先扩展正式组件库，再接入页面。
4. SVG 资产统一进入正式图标组件，不改为 Emoji 或外部 Icon Font。
5. 运营端与用户端共享基础 Token 和控件，但保留各自的导航、权限和内容边界。
